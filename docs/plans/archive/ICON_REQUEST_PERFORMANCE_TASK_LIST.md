## 3. \`IP-P0\`：范围与基线校准

### P0.1 核对普通图标请求边界

检查并记录以下符号的当前行为：

- \`src/lib/localBookmarkIconCache.ts\`：\`fetchBookmarkIcon\`、\`fetchObjectIcon\`、\`fetchObjectIconPayload\`、\`pendingObjectIcons\`、\`transientObjectIcons\`；
- \`src/lib/iconVisibility.ts\`：共享观察器和 \`rootMargin\`；
- \`src/lib/objectIconLoader.ts\`：可信设备的 \`limited\`、\`acquire\` 和释放逻辑；
- \`src/components/BookmarkCard.svelte\`、\`CachedBookmarkIcon.svelte\`、\`SpotlightBookmarkIcon.svelte\`：普通代理、可信副本、外部 \`<img>\` 的接线；
- \`src/lib/dataService.ts\`、\`src/App.svelte\`：\`applyLocalBookmarkUpsert\` 和后台刷新流程；
- \`scripts/perf-audit.mjs\`：C-5 图标请求统计和现有门槛。

输出：一张请求路径表，列出请求来源、是否可由本计划调度、缓存策略、鉴权边界和失败状态。

### P0.2 重新整理基线

把历史数据分为两类：

1. \`e865618\` 之前的历史重复请求基线；
2. 当前 \`v0.8.0\` 代码/部署记录中的 259 次请求基线。

每次新测量必须写明：构建标识、测试目标、日期、视口、登录状态、协议、网络条件、缓存状态、数据规模和操作脚本版本。

输出：基线表，不把 583 管理书签和 355 首页卡片合并成单一规模数字。

### P0.3 冻结不变契约

在实现前确认以下契约不能被性能改动改变：

- 普通 \`/api/icon/:id\` 的鉴权、\`no-store\`、edge 复用和回退头；
- 完整 URL 中 \`v\`、\`cv\`、\`key\` 的身份作用；
- 可信设备 \`/api/icon-local-copy\` 的四并发、租约、IndexedDB 和迟到写隔离；
- 现有 \`iconRetry\`、\`X-Icon-Fallback\` 和错误分类；
- Svelte keyed each、局部 upsert 和后台数据校准边界。

输出：实现前检查清单；若契约无法保持，停止并回到计划裁定，不直接编码。

### P0 出口

- 范围明确为 Issue #31 第 3 项；
- 普通、可信、分类、Iconify 和外部直连路径分开；
- 264 与 259 的时间关系已记录；

## 4. \`IP-P1\`：测量接线与固定夹具

### P1.1 定义会话指标

建议使用结构化事件或计数器，不在生产持久化：

| 指标 | 口径 |
| --- | --- |
| \`ordinary_started\` | 普通同源对象代理真正开始 \`fetch\` 的次数 |
| \`ordinary_in_flight_max\` | 普通代理请求同时未完成的最大数量 |
| \`ordinary_queue_wait_ms\` | 进入调度后到真正开始 \`fetch\` 的等待时间 |
| \`ordinary_body_ms\` | 收到响应头到正文读取结束的时间 |
| \`ordinary_duplicate_url\` | 完整脱敏 URL 在一次场景中的重复请求数 |
| \`ordinary_retry_class\` | 408、429、5xx、超时、连接中断、回退等类别计数 |
| \`first_view_ready_ms\` | 当前视口内首批可见图片达到既定就绪条件的时间 |
| \`long_task_or_frame_gap\` | Long Task 或超过 50ms 的帧间隔数量 |

指标记录必须区分普通代理和可信副本；对象 URL、密钥和书签内容只保留哈希或计数。

### P1.2 扩展只读审计

在 \`scripts/perf-audit.mjs\` 或独立脚本中增加：

- 普通代理请求时间线；
- 最大在途数；
- 精确重复 URL 的脱敏摘要；
- 首屏就绪和完整滚动阶段的帧间隔；
- 现有 C-5 门槛结果。

不得修改生产数据，不得因为采集指标增加额外图标请求。指标采集导致可见开销时，先关闭采集并保留原产品行为。

### P1.3 建立本地规模夹具

使用隔离 Worker/D1 或已有本地脚本生成三档可重复夹具：

- 150 个书签，模拟 Issue #31 的报告规模；
- 355 个实际可挂载首页卡片；
- 583 个管理聚合书签，但单独记录实际首页挂载数。

每档至少覆盖冷加载、完整向下滚动、回到顶部、快速往返滚动和搜索/Spotlight。生产环境不写入合成数据。

### P1.4 建立基线报告

每个场景至少运行 5 轮，保存中位数、P95、最大值和失败/清理结果。报告必须说明：

- 普通代理请求数和最大在途数；
- 首屏就绪时间；
- 50ms 以上帧间隔或 Long Task；
- 破图、文字回退、重试和重复请求；
- Cache Storage 和 object URL 清理。

### P1 出口

- L0 通过；
- 隔离 Chrome L2 至少一轮完整滚动通过；
- 当前是否存在“批量启动导致卡顿”的证据可复核；
- 如果问题不能复现，P2 只能做低风险测量改进，不能凭历史数字扩大优化范围。

## 5. \`IP-P2\`：普通代理有界调度

### P2.1 设计纯调度接口

调度接口至少需要表达：

- 普通代理 URL 或已脱敏的任务身份；
- 可见任务/预加载任务优先级；
- 任务开始、完成、取消和失败；
- 引用计数释放；
- 会话指标回调。

接口不得依赖 Svelte、D1、IndexedDB 或具体页面。调度器不拥有 Cache Storage 和业务数据。

### P2.2 保留现有缓存和安全语义

将调度接入 \`fetchObjectIconPayload\` 或其内部适配器时，必须保留：

- 同一完整 URL 只保留一个在途请求；
- 公开完成 Blob 的现有短期、有界复用；
- 带 \`key\` URL 不进入公开完成复用；
- 10 秒期限只覆盖真正开始的传输和响应体；
- \`X-Icon-Fallback\`、MIME、正文大小和 object URL 回收规则。

不得把调度器接入可信设备 \`objectIconLoader\`，不得把普通代理响应写入可信 IndexedDB。

### P2.3 实现并发实验

将 4、6、8 作为可配置实验参数。每档固定相同夹具、视口、网络和滚动路径，比较：

- 首屏可见图标就绪；
- 最大在途和排队时间；
- 50ms 以上帧间隔；
- 破图、回退和重试；
- 总请求和精确重复请求。

选择“用户可见就绪和滚动稳定性最优”的档位，不单独按请求总数选择。

### P2.4 接入组件生命周期

如果组件需要释放任务，使用引用计数句柄：

- 一个卡片释放不能取消另一个卡片仍在使用的共享请求；
- 未开始的预加载可取消；
- 正在传输的请求只有无引用时才中止；
- 迟到响应不能发布展示句柄；
- 组件销毁时所有 object URL 必须释放。

### P2.5 测试和回归

建议扩展或新增：

- \`tests/unit/localBookmarkIconCache.test.ts\`：在途合并、公开短期复用、私密隔离、超时和失败后重试；
- 独立纯调度单测：优先级、上限、释放、迟到结果和计时起点；
- 普通图标组件测试：公开/私密、卡片重复挂载、回退和取消；
- 隔离 Chrome：首页冷/热、完整滚动、回顶、搜索和 Spotlight。

### P2 出口

- L0 全部通过；
- L2 真实调用链证明普通首页确实使用了调度器；
- 可信设备和外部直连路径行为不变；
- 未引入新的长期缓存、全量预加载或隐私共享。

## 6. \`IP-P3\`：条件性失败冷却

### P3.1 立项判定

从 P1 报告中确认同一对象是否在短窗口内重复出现可重试失败。需要同时看到：对象身份/版本、失败类别、重复时间间隔和当前回退结果。只有“失败很多”而无法证明同一对象重复失败时，不立项。

### P3.2 定义冷却键和状态

建议以普通代理对象、内容版本和权限作用域作为冷却身份。公开和私密不能共享状态；版本变化应允许重新尝试。冷却状态只在当前页面会话内存在，不写 Cache Storage、IndexedDB、D1 或 KV。

### P3.3 接入明确重试出口

只允许以下出口触发一次重试：

- 页面重新获得焦点；
- 浏览器报告网络恢复；
- 用户显式编辑/重试；
- 当前卡片重新获得有效展示句柄。

不得使用永久轮询，也不得让冷却掩盖用户显式重试。

### P3.4 故障注入和单测

在本地隔离环境覆盖 408、429、500、503、连接关闭、超时、200 回退和恢复成功。单测确认：

- 冷却窗口内不会重复发起同一任务；
- 成功结果能清除失败状态；
- 错误正文不进入成功缓存；
- 401/403/409 和可信设备失败不被错误冷却；
- 组件销毁和登出仍能清理任务。

### P3 出口

输出“实施”或“不实施”的正式裁定。若实施，必须有冷却时间、失败类别和恢复入口的证据；若不实施，记录原因，不留下未接入的备用代码。

## 7. \`IP-P4\`：可见性窗口与局部更新

### P4.1 可见性窗口实验

保持 \`IntersectionObserver\` 单例，比较 160、240 和现有 420px。固定其他变量，分别记录：

- 首屏图标就绪；
- 快速滚动时的排队长度和最大在途；
- 回顶后的重复请求；
- 破图、回退和横向溢出。

如果所有窗口都没有可观测收益，保留 420px，不为改变数值而改变数值。

### P4.2 新增/更新书签调用链

在真实保存流程中记录：

1. 保存 API；
2. \`applyLocalBookmarkUpsert\`；
3. 首页 keyed 卡片变化；
4. 后台必要刷新；
5. 普通图标队列任务；
6. 2 秒内重复普通代理请求；
7. 最终图片或回退展示。

首页不应因为新增一张书签而整批重取已有普通对象图标。后台若需要全量校准，必须在报告中单独说明。

### P4.3 视口和入口回归

覆盖桌面和 390px 视口、首页、搜索、Spotlight、后台书签列表、取消新增、更新已有图标和分类切换。记录控制台、页面异常、失败请求和非预期 HTTP 状态。

### P4 出口

- 调度与可见性窗口没有造成首屏回归；
- 新增书签的首页真实调用链为局部更新；
- 后台校准和首页渲染的请求责任清晰；
- 桌面和窄屏布局没有新增错位或横向溢出。
