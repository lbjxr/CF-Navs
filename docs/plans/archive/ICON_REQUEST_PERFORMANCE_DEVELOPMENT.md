# 普通对象图标请求调度与首页滚动性能跟进计划

日期：2026-10-11
状态：待实现
范围：Issue #31 的首页滚动与图标请求性能部分
相关历史问题：[Issue #28](https://github.com/lbjxr/CF-Navs/issues/28)

本文是实现契约和验收依据，不记录当前工作项状态。状态仍以 [BACKLOG](../BACKLOG.md) 或 GitHub Issue 为准；提交、推送、部署和 Issue 生命周期操作分别需要明确授权。

## 1. 范围与当前判断

### 1.1 本计划只处理的内容

本计划只覆盖 Issue #31 中与首页大规模渲染、普通对象图标请求和滚动交互相关的部分。首页视觉定制、二级分类高频入口以及其它需求不在本计划内。

Issue #28 的文字图标回退、编辑后恢复、普通代理失败重试和可信设备副本恢复属于已有兼容性约束。本计划必须保持这些行为，不重新定义 Issue #28 的产品语义，也不把它当作本轮性能问题的根因。

### 1.2 必须先校准的基线

仓库已有的 v0.8.0 发布记录显示，\`e865618\` 之后公开对象图标增加了短期内存复用和在途合并，\`npm run perf:audit\` 的图标请求数为 **259，满足现有 260 门槛**。因此，早期观察到的 264 次请求只能作为 \`e865618\` 之前的历史基线，不能直接写成当前回归。

此前记录中的 583 个管理数据书签、约 355 个首页卡片、216 个新增图标请求、约 178 个同时在途请求以及图标耗时和帧间隔数据，也必须重新标明采集构建、站点、视口、登录状态、缓存状态和采集方法。583 是管理聚合规模，355 是页面实际挂载规模，不能当作同一个页面数量指标。

阶段 0 完成前，不把上述历史数字作为当前用户症状的证明，也不把 Issue #31 标记为已修复或已复现。

### 1.3 当前技术假设

若问题仍可复现，优先验证以下链路：普通 \`/api/icon/:id\` 请求在可见性闸门打开后批量启动，响应体读取、Blob 解码和卡片更新在滚动期间交错执行，造成网络压力和主线程长任务。这个假设需要通过请求时间线、在途数、首屏图标就绪时间和长任务数据验证，不能只根据 CSS 动画或总请求数推断。

## 2. 目标与非目标

### 2.1 目标

1. 在不破坏当前图标协议的前提下，限制普通对象代理图标的同时传输数量。
2. 保留当前普通对象请求的完整 URL 在途合并、公开短期成功复用和私密 \`key\` 隔离。
3. 只有在阶段 0 证明存在失败请求突发时，才为普通可重试失败增加有界冷却。
4. 验证新增或更新书签时首页是否只发生局部卡片和图标变化，并区分后台必要的数据校准请求。
5. 保持现有鉴权、租约、缓存头、内容校验、回退、迟到结果隔离和可信设备图标协议不变。

### 2.2 非目标

- 不把 503 改成 200，不隐藏真实失败状态，也不改变现有 \`retryable\`、\`unavailable\` 和 \`X-Icon-Fallback\` 语义。
- 不修改图标来源 URL、管理员数据契约、分类/书签排序和持久化格式。
- 不把普通代理响应写入可信设备 IndexedDB，不把私密 \`key\` URL 放入公开复用或共享统计。
- 不调度浏览器原生外部 \`<img>\` 请求，不做不可取消的全量预加载。
- 不把普通代理请求、可信设备 \`/api/icon-local-copy\`、分类图标、Iconify 和外部直连图标合并成一个失败或缓存策略。
- 不通过生产站点写入合成书签、批量物化或修改用户数据来制造性能数据。
- 不因为 L0、HTTP 成功或本地构建成功就声称 Issue #31 已解决。

## 4. 分阶段实施

### 阶段 0：范围校准与测量接线

- 记录当前构建、测试站、视口、登录状态、网络协议、缓存状态和数据规模。
- 把规模拆成管理总数、实际挂载卡片、图标槽位、唯一普通代理 URL、公开/私密数量和图标来源类型。
- 为普通代理请求记录会话内匿名指标：排队数、最大在途数、等待时间、传输时间、响应体读取时间、取消数、重试类别、精确重复 URL 数和首屏图标就绪时间。
- 不记录 URL 查询中的 \`key\`、Cookie、Authorization、书签标题或真实来源 URL；私密请求只记录脱敏分类和计数。
- 扩展 \`perf:audit\` 或独立只读脚本，保留现有 C-5 的图标请求 260 门槛，不改变业务请求和持久化行为。
- 使用隔离 Worker/D1 或现有本地回归夹具建立 150、355、583 三档规模；每档明确实际挂载数和图标来源，不把管理总数伪装成首页卡片数。

验收：测量代码达到 L0，并用隔离 Chrome 完成至少一轮 L2 真实滚动验证；输出能区分普通代理请求、可信副本请求、Iconify 和外部 \`<img>\` 的报告。没有可重复证据时，停止后续算法改动。

### 阶段 1：普通代理图标有界调度

- 只对 \`fetchObjectIconPayload()\` 所代表的普通同源对象代理请求增加调度，不接管可信设备、分类、Iconify 或外部直连路径。
- 先保留现有在途合并和公开短期复用，再增加 \`acquire/release\` 或等价引用计数接口，使未开始任务可取消、共享请求不会被单个卡片误取消。
- 以 4、6、8 作为实验档位，最终值由首屏就绪时间、长任务、帧间隔、错误和重复请求共同决定，不在编码前写成产品契约。
- 只有真正开始 \`fetch\` 后才启动 10 秒响应体期限；排队等待不消耗传输期限。
- 可见卡片优先于预加载卡片；预加载只能使用空闲槽位。
- 私密 \`key\` URL 不进入公开完成结果复用；迟到结果不得创建新的 object URL 或写入共享缓存。

验收：纯调度逻辑单测覆盖上限、优先级、在途合并、引用释放、超时释放槽位和迟到结果隔离；L2 覆盖首页冷加载、完整滚动、回到顶部、公开/私密图标和现有回退链路。

### 阶段 2：普通代理失败的条件性冷却

只有阶段 0 证明同一对象在短时间内发生重复可重试失败时，才实施本阶段。

- 冷却只适用于普通代理的 408、429、5xx、超时、连接中断以及现有协议明确标记为可重试的回退。
- 401、403、409、可信设备协议失败和永久权限结果不进入普通代理冷却。
- 冷却键必须保留对象、内容版本和权限作用域；私密请求不能与公开请求共享冷却。
- 冷却不写长期缓存、不污染成功 Blob；页面焦点、网络恢复和用户显式重试最多触发一次有界重试。
- 不引入永久轮询；服务端继续保持现有 HTTP 状态和缓存头。

验收：本地故障注入证明冷却窗口内不会重复请求，解除故障后能通过明确触发恢复；错误正文不进入 Cache Storage 或 IndexedDB；普通回退、编辑流程和可信设备链路不回归。

### 阶段 3：可见性窗口与局部更新验证

- 在阶段 1 稳定后，对现有 \`rootMargin: 420px\` 与 160、240px 做对照；至少比较首屏图标就绪、峰值在途数、滚动帧间隔、破图和请求总数。
- 保持 \`IntersectionObserver\` 单例和无 API 时的立即可见回退，不把所有图标改为 eager。
- 分别验证首页、搜索、Spotlight 和后台书签列表，不能用后台全量刷新结果代表首页局部更新。
- 新增/更新书签时记录保存请求、\`applyLocalBookmarkUpsert\`、后台校准请求、局部 DOM 变化、普通代理重复请求和最终卡片可见性。
- 保持 Svelte keyed each；只有真实调用链证明需要时才调整 store 或数据刷新流程。

验收：新增一张书签不会造成首页既有普通图标整批重取；后台必要校准请求有明确归属；桌面和 390px 视口无横向溢出、卡片错位或操作回归。

### 阶段 4：收口与部署后验证

- 固化最终调度上限、是否采用冷却、冷却时间和可见性窗口，并把选择依据写入测试输出。
- 完成 L0 和 L2 后，按仓库发版流程由 \`develop\` 推送触发 Cloudflare 自动构建；不把手动 \`npm run deploy\` 作为默认步骤。独立实例需要手动部署时，另行取得授权。
- 部署后运行 \`npm run accept:prod\`、\`npm run perf:audit\` 和本计划新增的只读性能场景，核对真实生产自定义域。
- 只在实现、L2/L3 证据和维护者授权齐备后更新 \`CHANGELOG.md\`、\`BACKLOG.md\` 或 Issue 生命周期。

## 5. 指标和验收门

### 5.1 保留的现有门槛

\`npm run perf:audit\` 的既有门槛继续有效：本站失败请求 0、破图 0、Cache Storage 不超过 5 MiB、普通图标请求不超过 260、管理员数据传输不超过 60,000 bytes、首页卡片数达到当前门槛。不得通过改变统计路径或放宽阈值制造通过结果。

### 5.2 新增性能指标

- 首屏可见普通图标就绪时间：中位数和尾部；
- 普通代理最大在途数和排队长度；
- 精确重复 URL 数，以及由对象版本变化合理解释的重复数；
- 50ms 以上帧间隔或 Long Task 数量；
- 普通图标破图、文字回退、可重试失败和最终恢复数量；
- 回到顶部、搜索切换和新建书签后的新增请求；
- Cache Storage 字节数和 object URL 清理结果。

不能只要求 P95 传输时间下降。若降低并发使首屏变慢或回退增加，即使总请求数下降也不通过；用户可见就绪和滚动稳定性优先。

### 5.3 验证级别

- **L0**：\`npm run type-check\`、\`npm test\`、\`npm run build\`、\`git diff --check\`。
- **L2**：隔离临时 Chrome 覆盖冷/热加载、完整滚动、回顶、搜索、Spotlight、新增书签、公开/私密和 390px 视口；记录控制台错误、页面异常、失败请求和非预期 HTTP 状态。
- **L3**：部署后重新运行现有生产验收和性能审计；普通代理性能改动未完成 L3 前，不宣称线上问题已解决。
- 受控 503、408、429、500、连接关闭和超时只在本地隔离环境注入；生产验收保持只读。

不纳入自动化结论：iOS Safari、真实移动设备、系统强杀、长期 24 小时租约和外部图标源永久下线。

## 6. 风险与回滚

| 风险 | 处理方式 |
| --- | --- |
| 普通队列上限过低，首屏图标变慢 | 用固定视口和网络条件比较 4/6/8；首屏就绪恶化时回退上限或撤销调度 |
| 共享请求被错误取消 | 使用引用计数；单测覆盖两个卡片共享同一 URL、一个先销毁的场景 |
| 迟到响应污染 Blob 或缓存 | 请求代次、会话作用域和有效句柄同时校验；迟到结果只允许被丢弃 |
| 冷却掩盖外部图标恢复 | 冷却只针对可重试普通代理失败，且有焦点/网络/显式重试出口 |
| 普通和私密缓存串用 | 完整 URL、对象版本和权限作用域分键；私密 URL 禁止公开复用和共享指标 |
| 新增书签误触发全量刷新 | 保持 keyed each 和局部 upsert；按首页、后台、搜索分别采集真实网络证据 |
| 测量代码本身造成卡顿 | 会话内轻量计数，默认不持久化；若开销可见，关闭采集而保留产品行为 |

回滚优先恢复阶段 0 前的普通代理请求路径；不删除历史缓存、不改变图标协议、不回滚无关的 v0.8.0 修复。

## 7. 实施前裁定项

以下不是预先选择的产品值，而是阶段 0 后必须根据证据回答的问题：

1. 普通代理调度是否真的能改善首屏和滚动；
2. 普通代理并发上限在 4、6、8 中取何值；
3. 现有 \`420px\` 可见性窗口是否需要调整；
4. 是否存在足以支持全局冷却的重复可重试失败；
5. 新增书签的首页路径是否存在无需全量刷新即可修复的真实重复请求。
